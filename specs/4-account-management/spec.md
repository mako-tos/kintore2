# アカウント管理（OAuth ログイン）

作成日: 2025-11-29 / ステータス: Draft / 対象ブランチ（想定）: `4-account-management`

## 目的

- Supabase Auth（Google OAuth）でログイン機能を提供し、ユーザーごとにデータ（TrainingMenus / TrainingRecords）を分離する。
- 既存データは最初のログインユーザーに帰属させ、以降はユーザー単位のRLSを厳格に適用する。

## 要件

- 認証: Google OAuth のみ（パスワードは扱わない）
- アカウント情報: Supabase の `auth.users` をソースオブトゥルースとし、アプリ用の `profiles` テーブルを別途用意（1:1）
- データモデル: `training_menus` と `training_records` に `user_id` を追加（初期は NULL 可）
- 初回ログイン後: 既存全レコードの `user_id` を最初のログインユーザーで一括更新し、その後 `user_id` を NOT NULL に変更
- RLS: 推奨 3 ポリシーを全て採用（SELECT/INSERT/UPDATE/DELETE を `user_id = auth.uid()` で制限）。サービスロールはフルアクセス

## スコープ

- このドキュメントでは仕様とデータモデル／移行方針を定義する
- UI 実装（ログインボタン、ログアウト、保護ルート）や API/リポジトリの改修は別タスクで対応

## 非スコープ

- パスワード認証、複数プロバイダのサポート
- 共有（パブリック）データ閲覧モード

## UI 要件

### ヘッダー改善

1. **タイトルリンク**: ヘッダー右側の `💪筋トレ記録` をクリックすると index ページ（`/`）を開く
2. **ログアウトボタン**: 見た目を周りのリンク（Navigation のリンク）と統一する
3. **ユーザー名表示**:
   - `profiles.display_name` が設定されている場合はそれを優先表示
   - `display_name` が未設定または NULL の場合は `user.email` を表示

## セキュリティ／プライバシー

- RLS でユーザー毎にデータを分離
- サービスロールキーはサーバ側のみで使用（クライアント配布禁止）

## リスク／注意点

- RLS を導入すると匿名（anon）ではデータを読めなくなるため、ログイン導線実装前は既存画面が閲覧不可になる可能性
- 初回ログイン者の選定ロジック（最初に成功したユーザー）にレースが起きないよう、バックフィル処理は一度だけ実行するガードが必要
